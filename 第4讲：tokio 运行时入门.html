tokio 运行时入门：让并发真正跑起来

第3节讲了 async/await 的语法长什么样，但代码还没真正"跑"过。这节我们用 #[tokio::main] 和 tokio::spawn 把并发落到实处，并用秒表量化它到底省了多少时间。

时长约 20-25 分钟
形式宏讲解 → 并发实测
前置第3节 async/await 语法
入口宏

#[tokio::main] 只是帮你少写几行样板代码

async fn main 本身不能直接运行——Rust 的 main 必须是同步函数。这个宏做的事情，就是生成一个同步 main，在里面创建一个 runtime，然后把你的 async 逻辑 block 在上面跑完。

💡
要点：runtime 就是那个真正"调度并推进"所有 Future 的执行器，宏只是帮你省掉手写 Runtime::new() + block_on() 这两步。
并发起飞

tokio::spawn：把任务交给运行时去调度

spawn 会把一个 Future 打包成一个独立的 task，交给 runtime 的调度器。多个 task 之间可以交替推进——这就是"并发"的来源。

实测对比

三个 1 秒的模拟请求：串行 3 秒 vs 并发 1 秒

串行耗时: 3.02s  （一个 Future 完全推进完才开始下一个）
并发耗时: 1.01s  （三个 task 交给 runtime 调度，可以交替推进）
收尾姿势

JoinHandle：两种等待多个任务的方式

tokio::spawn 返回一个 JoinHandle<T>，.await 它才能拿到任务的返回值。任务数量固定时用 tokio::join!，数量不固定时收集成 Vec 再逐个 await。
