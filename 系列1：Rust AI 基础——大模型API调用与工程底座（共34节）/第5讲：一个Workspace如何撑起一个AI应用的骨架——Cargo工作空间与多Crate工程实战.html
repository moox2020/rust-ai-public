开篇词

一个 AI 应用，远不止"调一次模型"那么简单

哪怕只是一个命令行问答小工具，稍微认真一点做，代码里也会自然长出好几块职责：处理文本的小工具、组装 Prompt 与调用模型的核心逻辑、接收用户输入的命令行入口。把它们全塞进一个 src/main.rs，很快就会分不清"哪段是能复用的能力、哪段只是临时胶水代码"。

这一讲，我们用 Cargo Workspace 把一个 AI 应用拆成职责清晰的几个 crate：工具层、业务层、入口层各自独立又能互相调用，为后面几节课要学的"真正接入大模型 API"打好工程地基。

基础概念篇 · 01

一个 AI 应用，塞进单个 Crate 会怎样

文本处理小工具、Prompt 组装逻辑、命令行交互全挤在一个 src/ 里，职责越来越模糊

只改了一行 CLI 参数解析，也要重新编译整个"巨石"AI 应用

想把"调用模型"的核心逻辑单独发布成库，给 Web 服务或另一个工具复用，却和 CLI 代码耦合，拆不出来

多个 AI 小工具各自一份 Cargo.lock，依赖版本对不齐

拆分之后：能力层可被别的 AI 应用直接复用，入口层随便换

基础概念篇 · 02

Workspace 结构解剖图

根 Cargo.toml 只用 [workspace] 声明"这里有哪些成员"，本身不产出任何二进制或库；所有成员共享同一份 Cargo.lock 和同一个 target/ 输出目录，避免重复编译、避免版本分裂。

根目录只放"共享的东西"，每个成员自带一份完整的 Cargo.toml 与 src/

基础概念篇 · 03

每个成员，都是一个独立的 Crate

lib crate

库 —— 提供 AI 能力

入口是 src/lib.rs，没有 main 函数；产出可被其他 crate 依赖的库，是"可复用的能力单元"。例如封装 Prompt 组装、模型调用抽象的 ai-core，与提供文本工具函数的 ai-utils。

bin crate

二进制 —— 面向用户

入口是 src/main.rs，包含 fn main()；编译出可执行文件，是"面向用户的入口"。例如接收用户提问、调用 ai-core 的 ai-cli。

workspace 不限制成员类型的比例。AI 应用里健康的组合通常是"多个 lib（能力）+ 一个 bin（入口）"——今天入口是命令行，明天想换成 Web 服务，只需要新增一个 bin crate，ai-core 与 ai-utils 原封不动地复用。

基础概念篇 · 04

依赖，怎么管才不乱

上层统一声明版本，下层用 workspace = true 继承；crate 之间再用 path 互相调用

统一声明：根 Cargo.toml 的 [workspace.dependencies] 里写好每个依赖的版本，例如 anyhow、clap，全仓库只声明一次

继承版本：成员 crate 里写 xxx = { workspace = true }，版本升级只改根目录这一处

本地互相依赖：crate 之间通过 path = "../ai-utils" 联调，不必先发布到 crates.io 也能本地跑通

基础概念篇 · 05

根 Cargo.toml 关键字段速查

[workspace]

members 列出所有成员目录，是这份文件的核心。

resolver = "3"

使用新版依赖解析算法，避免不同成员因 feature 合并产生的隐性冲突，新建 workspace 建议显式声明。

[workspace.package]

统一 edition、version、authors，成员用 edition.workspace = true 继承。

[workspace.dependencies]

统一声明第三方依赖版本，成员用 = {workspace = true} 继承。

path 依赖

成员之间互相引用，用相对路径指向兄弟目录，本地联调零成本。

Cargo.lock 唯一

整个 workspace 只有一份，成员之间依赖版本天然一致，不会打架。

# 根 Cargo.toml 骨架（精简示意） [workspace] resolver = "3" members = ["ai-utils", "ai-core", "ai-cli"]
基础概念篇 · 小结

概念一图记

一份根 Cargo.toml 用 members 统领多个 crate，共享 Lock 与产物目录

成员分 lib（能力）与 bin（入口）两种角色，各自独立又互相调用

依赖版本向上统一声明，crate 之间用 path 本地联调

代码实操篇

生产级案例：三 Crate 分层的 AI 问答工具

目标：搭一个命令行 AI 问答小工具 ai-cli，内部依赖负责"组装 Prompt、定义模型调用抽象"的 ai-core，再往下依赖纯文本工具 ai-utils。本讲还没学到真实的网络请求（后面模块会学），这里先用可预测的 Mock 客户端把"调用大模型"的接口占好位置。

依赖方向单向：cli → core → utils，utils 是最底层，不反向依赖任何人

ai-core 里的 LlmClient trait 是"面向接口编程"的关键——今天接 Mock，以后无缝换成真实模型

anyhow / clap 版本统一写在 [workspace.dependencies]，三个成员各自继承
